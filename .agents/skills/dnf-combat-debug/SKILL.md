# DNF 战斗排查

从当前仓库根目录执行。先读 [AGENTS.md](../../../AGENTS.md)、[协作总纲](../../../docs/project/00_协作总纲.md) 和 [28 分工](../../../docs/design/28_工作区分工与原版资料共享.md)。工作区身份从 `.workspace` 读取，技能名称不授权修改其它区模块或发送消息。

## 复现与定位

- 记录入口场景、代码 SHA、资源来源、角色/装备、怪物 ID、朝向、横向/纵深/高度、输入序列以及预期和实测。以当前 diff 和运行结果核对状态文档，旧报告是历史证据。
- 从最小独立战斗场景复现，再判断是否需要完整循环。读 [战斗内核实装](../../../docs/design/29_新版工程框架_战斗内核实装.md) 中对应部分和相关测试，保留能暴露故障的断言。
- 沿输入 → 动作时钟 → 选招/移动 → 攻防盒 → 命中/伤害 → 事件 → 表现追踪。区分世界脚点、纵深、物理高度和屏幕坐标；攻击与 AI 停靠必须比较同一招式、朝向及坐标系。对时序问题记录帧和状态变化，区分模拟时间、局部 hitstop、暂停及真实时间。
- 原规则不明确时按 [原版拆解路线](../../../docs/design/26_DNF原版拆解与还原路线.md) 标注证据等级。先追 CHR/SKL/MOB/ATK/ANI/ACT/AI 来源，不凭文件名或“脚本存在”认定行为已恢复。

## 工具选择

- 独立回归：`powershell -NoProfile -File tools/run_dnf.ps1 -Test`；需要实际渲染证据时加 `-Capture`。该入口固定 Godot 版本、战斗场景及成功标记，检查退出码和完整结果。
- 架构检查：`python tools/check_dnf_deps.py`；中文扫描：`python tools/check_game_chinese.py`，原图文字仍要看截图。
- 表现回归使用 `tools/trace_dnf.ps1 -Label <标记>` 与 `-Compare <基线标记>`。先读脚本：它使用工程主入口；与独立战斗入口不一致时明确场景条件，不直接比较不同入口的轨迹。只有表现预期不变的改动才要求轨迹相同。
- 可用 `godot-dnf` MCP 时，先 `check_project` 核对路径和版本，再检查当前会话。诊断使用 `run_project`、`get_debug_output`、`take_screenshot`、`get_ui_elements`、`run_script`、`simulate_input`。先读取节点/属性再构造输入；监视脚点、动作、冷却、AI 状态、命中计数。临时诊断通过现有 debug API，生产调用仍遵循模块 API 边界。
- MCP 运行会临时注入 autoload，截图/桥接位于工程 `.mcp` 目录。按当前工具 schema 调用，测试结束 `stop_project`，确认 autoload 清理、工程配置恢复且无桥接文件被 stage。显式释放跨调用持有的输入。
- MCP 输入/截图、普通回归和用户试玩分别记录。输入注入并不证明操作系统真实输入；视觉与手感认可仍由用户确认。

## 修复与交付

选择能解释根因的最小修复，保留身体/武器/特效/命中共用时钟和暂停语义。仅跑与改动相称的检查；跨模块接口变更再做接入验证。报告原始失败、修复后结果、仍未知项和可回放证据。是否提交/推送、占位、状态回写及交接一律按协作总纲执行。
