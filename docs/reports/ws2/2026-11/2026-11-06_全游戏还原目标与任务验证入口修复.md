# 全游戏还原目标与任务验证入口修复

用户将目标扩展为原版DNF几乎全部功能与表现近乎一致，并要求开始持续执行。参照沿用用户指定的D盘“纯60复古”；代码、配置和资源引用优先。已建立持续目标，当前仍在执行，未完成整版复刻。

## 一、接续与范围

- 以设计49的当前执行目标和SYS-00～18全系统目录统筹；技能、战斗、UI、系统、任务、副本、城镇均在范围内。
- 不重复建立一份独立“完成度百分比”；既有目标候选、可解析、可运行和用户验收仍分别统计。
- 现有机器基线的技能运行计数只读取旧numbers/combat层，未覆盖后来生成的skill_runtime合并；在修正这项口径前，不用该数字判断技能还原程度。新增运行定义也不自动代表行为正确。
- content/api迁移已在本机消费，扫描没有旧native_catalog/weapon_appearance路径或Numbers.config调用，依赖与性能检查通过；本区确认接收并关闭旧等待项。
- 既有project.godot修改和未跟踪items_v1保持原样。

## 二、复现正式入口阻断

`tools/build_dnf_quest_rules.py --check`此前报Quest v2 definitions/audit are stale，导致正式流程包装脚本无法跑完，只能绕到专项入口。

逐字段重建后确认：任务定义、审计JSON、目录内容均完全一致；已有gzip与当前Python 3.13生成结果等长20598字节，解压内容逐字节相同。唯一差异在gzip头偏移9，旧值10、新值255，导致压缩包SHA以及runtime内的status_sha256比较失败。

这是压缩平台标记差异，不是任务规则、原始QST或执行依赖发生变化。直接重写整个任务包会掩盖这个跨环境问题。

## 三、修复契约

- 验证状态包时，解压内容必须与从原任务重新编译的规范JSON逐字节一致。
- runtime记录的压缩包SHA必须与实际落盘字节一致；不因为解压内容相同而忽略文件哈希错配。
- runtime其余字段、审计和目录仍须与重建结果一致；报告具体不一致文件。
- 新构建的gzip平台字节固定255；已有合法包无需重新压缩或重写。
- 未修改任务奖励、目标、前置、源索引、状态包或个人存档。相关Python测试接入CI。

反例测试覆盖Linux/Windows/unknown平台标记、不同压缩级别、内容修改后重新计算SHA、压缩字节变化但未更新SHA、损坏和缺失包。前两类内容与记录一致时通过，其余必须拒绝。任务语义与包校验共12项通过。

python tools/test_dnf_quest_rules.py
