## 范围与交付

不是换一套美术，也不生成新图片/音频。
本轮共同规范适用新版；旧版C10、V7、旧HUD/副本验收与待办不合并为原版事实。
共享完整库只作来源之一；当前来源缺口见[证据与版本](../../design/26_DNF原版拆解_证据与版本.md)。

| 子任务 | 输入与产出 | 可认领边界 | 完成条件 |
|---|---|---|---|
| T0 来源锁定 | 客户端入口/哈希、有效PVF、补丁顺序、配套关系 → 参照来源清单 | 一区负责来源记录，原始文件只读 | 可重复启动/观察；有效配置有加载证据；冲突保留 |
| T1 全内容与依赖 | LST/CHR/SKL/MOB/DGN/MAP等 → ID台账、引用图、有效内容候选 | 一区维护解析/台账；不改战斗模拟 | 原ID可追到原文件；动态/缺失/多候选显式分类 |
| T2 场景与美术对照 | 一间原版MAP/TIL及录像 → 原房间装配、相机/比例/层序、四向门 | 可独立研究场景与资源；共同坐标由T0/T1协调 | 同路线全屏对照，前后遮挡/滚动/走区正确 |
| T3 UI对照 | 原整屏/状态截图、UI/图标/字体来源 → HUD布局与控件状态表 | 可独立维护UI规格与素材选中表 | 原布局/图标/字形/遮罩/焦点有依据；全屏验收 |
| T4 动作与战斗对照 | 同角色/装备输入录像、ANI/CHR/SKL/ATK → 帧事件、状态/判定/受击规则 | 一区负责模拟接口；输入/动作/判定变更协调提交 | 空挥/命中/取消/受击均有原版与Godot对照 |
| T5 单机系统规则 | 任务/装备/物品/经济/存档来源 → 模块规则与生命周期 | 可在R1期间先做文档/台账，不擅改未定公式 | 条件/事务/失败/持久化明确，未知项不伪装默认 |

T2/T3/T4的离线调查可以并行；实装都依赖同一版本、坐标与时钟契约。
不得让不同工作区同时各改一套main.gd。按[协作总纲](../../project/00_协作总纲.md)登记占位并认领本区产出。
需要多区协作时通过既有交接与状态文件发布，不能把本文建议当作其它区已接任务。

## 首批还原样本

1. 原版实际开放的一名鬼剑士，固定等级、技能等级、衣装和一把武器；具体选择写入来源记录。
2. 同一张真实森林地图中的一间房，含完整背景/图块/物件/门/音乐；不能沿用现版验证布局充当原房间。
3. 一种经原ID链确认的普通怪物；不能直接把goblin.mob或同名ACT等同于现版图像。
4. 基础动作、三连、上挑、拔刀及一项多段技能；目标版缺项则登记替换样本的理由。
5. 同版本原HUD和该样本用到的UI状态；其它界面在全系统台账继续拆解。

样本用于覆盖基础能力，不代表目标只做一个职业/房间或删掉其它系统。

## 每份交付包的内容

- 来源身份、SHA256、规则/差异ID、适用条件与原始字段定位。
- 解析结果与未支持项；依赖清单、版本与接口变化。
- 原版与Godot的相同输入序列、整屏静图、连续视频、关键事件对照与误差。
- 失败/打断/缺资源/缺蓝/死亡/重开/切房等适用边界。
- 未知项、适配项、下一位接收方要做的检查；不能仅写“测试通过”。

媒体使用当前实际导出与实装同包；大体积资源与录像沿用外部资源/本地证据方式，不塞进源码Git。
没有原版实机证据时可以交结构调查，但任务仍保留实机缺口。

## R1验收

按[固定回放集合](../../design/26_DNF原版拆解_表现与战斗对照.md#六r1固定回放集合)逐项交付。
分别核场景/美术、UI、动作、战斗，不用某一项通过抵消另一项缺陷。
接收方完成本机运行验证，用户确认展示范围后再登记已验收。
此前视频验收继续有效于原展示范围，不据此省掉本轮原版一致性比较。
