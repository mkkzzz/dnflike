# DNF 原版复刻并行计划

两区按可独立交付的模块分工。每区负责自己任务的开发、回归、验收和发布。新任务以当前可取得的资料和已发布的接口开工。完整目标仍覆盖技能、战斗、界面、系统、任务、副本和城镇。 [分工契约](../../design/28_工作区分工与原版资料共享.md)

上一批 ws1 系统模块的开发、自验和发布已结项，后续缺陷按原文件归属维护。项目级真人试玩和用户体验反馈独立记录。本轮两区都做内容还原，按原版取证、依赖确认、实装调校和回归的实际投入排程。

| 工作区 | 内容主线 | 首个可交付切片 | 后续队列 |
|---|---|---|---|
| ws1 | 天空之城副本、怪物和领主还原 | 龙人之塔 `draconiantower`。先闭环领主 `lakius` 和普通怪 `mirkius`，再完成当前正式路线剩余怪物和房间战斗 | 人偶之塔 → 石巨人塔 → 城主宫殿。复用已结项的同源怪物，只补各图的阵容与时序差异 |
| ws2 | 鬼剑士技能还原及原客户端取证 | 收魔狱血刹和暴风式剩余高风险分支，按招式分别发布 | 剑魂、狂战士其余核心招式 → 共通招式 → 鬼泣、阿修罗。觉醒任务、技能解锁另排 |

两条主线各先安排约 10 个工程小时，作为首轮排程窗口。分别记录原证和依赖、行为分支、声画调校、回归、等待时长，按首个切片实耗重估余量。两区共用 rainmk 的实机时间，原客户端采样按批合并。缺少证据时登记具体路径、触发条件和所需记录，继续本包内输入齐备的条目。

每只怪以正式 MAP 引用的 MOB 身份为准。逐招核对选招与距离、起手与冷却、动画帧、ATK 判定与受击、特效音效、退出与清理。召唤、阶段、投射物等按该身份的实际证据处理。每张图核对房间阵容、门与清场、领主、结算回城。现有普通路线和任务专线用不同用例，1～16 级完整试玩独立登记。

ws1 负责这些怪物的内容数据、专属行为、资源和测试，并自行完成正式房间自验。优先沿用 [ContentDB](../../../game_dnf/content/api/content_db.gd) 的分层数据入口、现有图集与 [CombatSession](../../../game_dnf/combat/api/combat_session.gd) 的房间入口。先验证首只怪的按 ID 变更能走正式路径，确认后再批量做。仅怪物专属文件由 ws1 独占。共用入口、同名生成物及正式路由由 ws2 写入，共用改动按首批需求集中提交，ws1 自验集成后的房间。只有原客户端才能确认的行为由 ws2 按清单录制或取证，ws1 登记证据适用范围。缺 haze 原图的 act8 留在原阻塞项。

## 并行边界

1. 每项开工记录基准提交、可写文件和本区验收入口。两区使用发布的资源和接口作为只读基线，禁止同一文件或生成物并行写入。
2. 发现跨界问题时，在本区报告记录路径和复现条件，文件持有方自行修复、测试和发布。独立任务遇到跨界需求时，只做已闭合的本区范围。
3. 各区自验各自发布的内容。已有原档和正式入口的内容直接开工。缺少原客户端证据或共用入口支持的具体分支单列，按各自的依赖关闭。
4. 验收记录区分自动化、原版对照和实际操作。共用入口与依赖变更由 ws2 自行验证，包括现行窗口和装备服务调用的兼容性。共用测试由 ws2 维护，各区维护本区专属测试并自行发布结果。各区旧状态中的跨区验收安排以本页为准。
