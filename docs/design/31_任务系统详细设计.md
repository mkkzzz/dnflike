# 任务系统详细设计

入口：[前期世界设计](30_前期任务城镇与NPC设计.md)、[工程接口](29_新版工程框架_接口契约.md)。

## 一、完整性与边界

30号文档是原包取证、任务关系和分批计划，不是足以直接照写的系统规格。本页补齐首批规则、数据、事件、事务、迁移与验收契约；不代表整个60级版本已还原。

首批原任务白名单为101→102→103→4301，接交人物是赛丽亚与林纳斯。原字段来自[取证快照](../reports/ws2/2026-10/2026-10-23_前期世界原包字段.json)，运行定义见[data/quests.json](../../game_dnf/data/quests.json)。原任务文本/参数与适配数值分开，保留源路径、原ID和SHA。未解释的任务类型不启用。

后续已按同一契约接入[34赫顿引荐](34_城镇联通与赫顿首批.md)和[36格兰首段](36_格兰之森首段与原副本编排.md)；启用节点以运行定义为准，新增篇章不改写首章历史，也不提前启用尚无对应副本/目标处理的凯诺段。

## 二、定义与状态

定义由quests/catalog.gd读取，进度由quests/service.gd管理，不让UI、战斗内部或存档工具各维护一份状态。

| 层 | 契约 |
|---|---|
| 内容版本 | schema=dnf_quests/1；revision是内容修订，不能替代存档迁移 |
| 任务键 | 稳定语义ID，不能用中文名或数组位置；source保存原包证据 |
| 前置 | requires内全部任务completed，且满足min_level；目前无OR、职业互斥或自动接取 |
| 目标 | 稳定objective.id、type、target、amount；可限定dungeon/difficulty；所有目标AND |
| 进度 | profile.quest_state，revision=1；entries、transactions、tracked均随角色保存 |
| 条目 | state仅active/completed；progress按目标键计数，seen按目标保存已处理事件ID |
| 派生状态 | 无条目时locked/available；active且全部目标与材料成立时ready，否则active |
| 一次性结算 | quest:语义ID:once；奖励与完成标记在同一角色快照，不按通关次数代替 |
| 容量 | 同时12条、追踪3条为E-ADAPT配置，不声称是原版上限 |

READY不另存布尔值：材料出售、装备占用或条件失效时必须立即退回进行中。完成任务不可再次接取。主线首批不可放弃；可放弃支线删除自身目标和追踪，重新接取从零开始。

加载校验必须覆盖重复键、引用缺失、依赖循环、不支持目标、非法数量、目标字段与事务不一致。未知的退役任务条目保留，不参与启用内容计数；不能因此清空整个人物。已知目标更名或删除必须另写迁移，不能静默重置。

## 三、命令与界面

| 命令 | 输入 | 校验与效果 |
|---|---|---|
| quest.accept | id | 城镇、正确接取NPC、真实距离、可接/容量；新建进度，空余时自动追踪 |
| quest.claim | id、可选choice | 城镇、正确交付NPC、距离、READY、库存与选奖；原子消费、奖励、完成、解除追踪 |
| quest.track | id | 进行中或可交付；城镇和战斗均可切换，超过容量要提示 |
| quest.abandon | id | 城镇、显式允许；主线拒绝，支线由界面确认后执行 |

命令上下文由外层会话根据当前场景生成，不能信任按钮自行填的nearby=true。打开Q列表不等于与NPC会面，也不能远程接交。列表可查看远方可接任务，但操作必须到人物旁。

Q任务窗复用原包任务底板、列表、按钮和中文字体；三页为可接受/进行中/已完成。列表保留选中项；详情含名称、委托人/交付人、描述、目标数量和奖励。按钮状态反映任务状态；鼠标连点与重新打开窗口不应重复发奖。奖励物品复用已有物品控件和详情，不单独绘制假图标。

NPC对话放画面下方，使用对应原大立绘（林纳斯frame0、赛丽亚frame1），原尺寸与底板边缘对齐。NPC只列实际开放的服务；赛丽亚不显示铁匠商店。追踪展示目标名称与数量，可交付时指向交付人物。NPC可接与可交标识根据当前角色实时派生，不按打开窗口次数累积。

## 四、目标与事件

所有事件只推进已接受且未完成的任务，不追认接取前击杀/通关。会面必须由实际交互产生，不由距离检测自动推进。多个已接受任务可以独立消费同一死亡事件。

| 目标 | 事件 | 精确判定 |
|---|---|---|
| meet_npc | npc.met | 指定npc；进入其对话时触发一次；接任务本身不算会面 |
| kill_monster | combat.monster_defeated | 原MOB路径匹配；当前run_id/room_id合法；副本/难度匹配；每次死亡只计一次 |
| clear_dungeon | dungeon.cleared | 指定地下城完整胜利结算；失败、撤退、普通房清怪不算 |
| collect_item | 库存快照 | 当前可提交数量，允许先拥有后接取；装备占用不可消费；交付时再次检查 |

事件必须有非空event_id。死亡优先使用战斗事件唯一标识，并包含run/room/entity作稳定去重；房间切换回访不能重生奖励。怪物投掷物、死亡特效和测试按钮不直接产生任务计数。计数达到amount后不再记录额外事件，避免无限增长。

宿主先核对当前运行身份，再给任务模块附上可信的dungeon/difficulty；模块自身不依赖战斗节点。副本最终胜利在通关事务内生成一次dungeon.cleared；通关奖励与任务交付奖励是两个不同事务。

## 五、奖励与存档事务

奖励适配器复用数值系统Numbers.Growth.grant、现有物品目录和布局规范；任务模块不再写等级经验公式。金币、XP、固定物品和选奖可组合；有选奖时必须提供有效choice，取消不变化。当前未有限背包容量，不做满包丢失或邮件补偿；将来有限格前必须增加预检/替代投递设计。

交付流程：复制角色快照→重新校验条件→消费材料→发放完整奖励→登记任务事务/完成→校验→写临时文件并原子替换存档→替换活动会话。保存失败保持原金币、经验、物品和任务状态，可重试；禁止先改活动角色再忽略write返回值。完成记录与奖励事务不能分文件。

接取、放弃、追踪沿用同一候选提交。战斗死亡已发生，保存失败不能撤销世界：目标保留在活动内存，显式标记未保存并允许重试；不能提示“已保存”。中断战斗重进城镇，不补通关奖励；已成功保存的击杀保留。

旧dnf_loop_save/1与/2的profile.quest只迁到legacy.trial：active保留进行，ready保留可交，done登记已完成但不补发奖励。旧委托完成不等于原任务101或102完成。旧金币/经验/装备/数值系统事务全部保留。每个角色独立账本，切人不串任务。

## 七、完成判据与后续缺口

- 单元：前置/等级、错误NPC与距离、错误副本/难度、重复死亡、重复交付、失败奖励回退、选择奖、材料失效、容量与旧档隔离。
- 集成：真实会话和数值奖励、保存失败全回退、备份恢复、切人；战斗公共信号到目标计数，通关与撤退分支。
- 实机：新建→赛丽亚→林纳斯→洛兰→回城交付→深处击杀→赛丽亚；Q列表、追踪、对话和中文原素材布局截图。
- 跨区：新资源必须进入不可变共享包，fresh consumer能启动；Git只含代码/配置/来源与版本锁，不依赖ws2私有绝对路径。

首批实现与实机证据见[本轮交付](../reports/ws2/2026-10/2026-10-23_首批原任务闭环与共享.md)。

本页给出首批可执行规格。完整任务系统后续还需：职业/互斥表达式、重复/日常周期、任务物品专用背包、掉落规则、地图事件与救援NPC、分解事务、转职奖励、服务解锁、有限容量投递和各版原奖励认证。未实装内容不能只凭定义存在标记为已完成。
