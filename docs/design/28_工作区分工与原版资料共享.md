# 工作区分工与原版资料共享

> 用户2026-10-22明确指定：ws1迭代战斗，ws2跑通完整游戏循环；只有ws2有原版环境，相关开发资料须上传供其它区使用。
> 本页是本轮分工与代码责任的唯一入口，覆盖26/27和旧接入任务中的历史分工建议；不代填其它区的执行/接收状态。

## 一、分工

| 工作区 | 负责 | 交付目标 |
|---|---|---|
| ws1 | 输入、角色动作、普攻/技能、判定、数值应用、怪物AI、受击/死亡、战斗特效/声音触发、战斗HUD与回归 | 同条件战斗连续可玩，规则/表现差异有依据，向流程侧输出真实事件 |
| ws2 | 城镇、出征/副本编排、地图接入、清房/门/切房、胜负结算、NPC/任务、背包/装备服务、奖励/成长、本地存档与整流程集成 | 城镇→出征→战斗→领奖→回城→整备→保存→再出征 |
| ws2 原版资料供应 | 原版身份/加载关系调查、原始数据与依赖、规则说明、对照媒体、已知差异和工具发布 | 交接内容可从Git仓库/资源Release取得，不只存在本机或聊天中 |
| ws3 | 按用户后续安排参与，既有工作保留 | 不擅自给ws3分配新任务或改其状态 |

ws1已发布的T2地图成果保留。后续地图/城镇接入由ws2承接，ws1重点转入战斗，避免继续被场景任务分散。
战斗与完整循环可并行开发；未知原版规则记录证据缺口，不能把整个工程等待在“先逆向全部程序”。
任务入口：[ws1战斗迭代](../tasks/design_tasks/ws1_combat_iteration_v1.md)、[ws2完整循环](../tasks/design_tasks/dnf_playable_loop_v1.md)。

## 二、文件与接口边界

| 范围 | 本轮责任 | 规则 |
|---|---|---|
| main.gd、combat.json、native_actor.gd、native_effect.gd、test_drive.gd | ws1战斗侧 | 当前main还混有切房/结算；ws2不与ws1同时改它 |
| native_hud.gd | ws1战斗HUD | 角色/技能/CD/怪物反馈；城镇、背包、正式结算UI由ws2另建 |
| export_dnf_map.py、native_map_loader.gd、native_stage.gd与地图数据接入 | ws2流程/世界侧 | 以ws1已发布T2为基线接收，保留来源/诊断；不替ws1填原版一致性验收 |
| 新增流程根场景、session/profile/save/items/rewards/town模块 | ws2 | 在战斗场景外编排，避免修改战斗主文件；首轮独立循环见[实装记录](../reports/ws2/2026-10/2026-10-22_原生素材城镇循环首轮实装.md)，新combat/api仍待ws1 |
| main.tscn、project.godot、run_dnf.ps1及共同接口 | 接入时单区占位 | 独立战斗验证入口保留；切主入口需同步更新战斗与流程验证方式 |
| 原始资产、构建器、发布锁与解析公共工具 | ws2供应，具体变更可交接 | 新版本不可覆盖旧字节；共享接口/字段变更须先写契约和影响 |

“文件归属”用于避免并发冲突，不能让同一文件长期保留两套互相矛盾的流程控制。
main.gd中遗留的切房/结算/重新挑战过渡期仍在战斗侧维护；外部管理模式需要的桥接由ws1按约定实现，或明确一次性移交后再改。
ws2优先新增外层流程，不通过修改main内部状态字典绕开协议。

首轮过渡桥：game_dnf/flow/legacy_combat_port.gd由ws2新增，继承现版主脚本，旧字段知识仅封装在此桥内；外层只调用start_run、snapshot、apply_heal、set_paused/stop_audio和flow_event。
这是用户要求先做循环时的独立兼容实现，未修改main，也不宣称29的combat/api已实现。现版五房/门仍由旧战斗负责，ws1新API发布后替换桥并迁移世界编排；不得把桥继续扩成第二套战斗内核。

## 三、战斗与流程的共同接口草案

以下为拟实现接口，不冒称现版已有这些方法/信号。双方先锁定v1再接入：

| 方向 | 接口与字段 | 职责 |
|---|---|---|
| 流程→战斗 | 开始房间：run_id、room_id、角色战斗属性快照、技能/装备映射、实体出生记录、地图坐标契约 | ws2给数据，ws1初始化战斗；不重置长期Profile |
| 流程→战斗 | 暂停/恢复、停止/卸载、合法属性或消耗品效果请求 | 只影响指定战斗会话；状态/资源校验有明确失败结果 |
| 战斗→流程 | monster_defeated：run_id、room_id、entity_id、原怪物ID及位置 | 击杀事件不直接发金币/经验；ws2按稳定事件ID提交收益 |
| 战斗→流程 | room_combat_finished、player_defeated：run/room标识、统计与角色状态快照 | ws2判断门/领主/结算/回城，ws1不直接写存档或切城镇 |
| 战斗→流程 | 战斗读视图：HP/MP、CD/Buff、角色/怪物状态与统计 | 战斗HUD消费；跨场景携带字段由Profile/Run规则决定 |
| 世界→战斗 | 地图根坐标、走区/阻挡、有效门区域、相机变换 | ws2提供世界查询或稳定数据接口；双方只转换一次高度/屏幕坐标 |

伤害/命中/状态由ws1计算；装备/等级的持久数据由ws2管理，再通过战斗属性快照供ws1使用。
奖励、任务、背包和存档只有流程事务入口，防止战斗事件与结算按钮双重发奖。
战斗场景单独运行时可以保留验证用默认初始化；外部管理模式不得自动出征、领奖或重开。
两区各测自己模块，再做同一入口的成功/失败/重载连续验证。

## 四、资料必须可共享

| 内容 | 发布位置 | 必须携带 |
|---|---|---|
| 代码、设计规则、ID/字段表、依赖/差异、操作说明、任务包 | 主仓库main | 稳定文件入口、适用版本、规则/差异ID、未知项 |
| 原图/音频/视频、原配置、数据库、说明原件和大体积对照媒体 | 独立私有资源库的不可变Release | 资源版本、清单、字节数、SHA256、同步命令 |
| 小型可共享实机证据 | 主仓库证据目录或同样的资源Release | 原版/Godot来源、角色/地图/装备条件、输入与时间基准 |
| 临时分析输出 | temp生成，结论/工具/必要源数据发布 | 可复现命令；不得要求其它区访问ws2的temp或127.0.0.1 |

不得让其它区承担必须依赖某份尚未发布资料的任务。缺口显式列入共享清单，由ws2补提取/发布/交接，不留在聊天承诺中。
已提取完整资源与数据库使用asset_store.json；补充原版说明/物品代码等使用reference_store.json，二者独立，不重装或改写游戏消费副本。
新增城镇/NPC/UI派生运行图与实机证据使用game_dnf/flow_store.json及tools/sync_dnf_flow.py；小包无需完整库，独立安装戳不改基础运行戳，可加--evidence取得共享截图/检查日志。
入口清单是game_dnf/source_materials.json；其中记录原始PVF三份、数据库、声音映射、补充文档及仍待取证内容。

```powershell
python tools/dnf_asset_store.py sync --full
python tools/sync_dnf_references.py
```

首次各区自行验证与登记接收。ws2发布成功不代表其它区已同步。
用户授权本项目相关资料共享；凭据、私钥、个人存档不入库。未证实配套的DNF1031服务端不混入本版数据；后续实际依赖它时先完成识别和可共享资料提取。

## 五、持续更新与当前缺口

原始数据变化 → 生成来源/依赖/字段变化记录 → 发布不可变资源版本 → 主仓库锁与任务入口更新 → 接收区本机校验 → 集成回归。
原版运行对照、实际生效PVF选择、服务端对应规则仍未全部查明；共享已有原文件不等于这些问题已解决。
新取得的设计/数值/录像当轮发布必要内容与复现入口，不把ws2变成每个文件都要人工转发的瓶颈。
需要其它会话行动时，用户可将对应任务口令发送到该会话；本页更新本身不声称已发送或对方已接任务。
