# 城镇、副本与战斗闭环

> 适用新版game_dnf。目标是用户可连续游玩的本地流程；原版品质按[26还原路线](26_DNF原版拆解与还原路线.md)同时推进。
> 本页为项目闭环规格，不将未核实的流程/数值写成原版事实。

## 一、目标与当前缺口

目标流程：启动/读档 → 城镇 → NPC任务/补给/整备 → 选择副本 → 入场与逐房战斗 → 领主 → 结算领奖 → 回城交任务/换装备 → 保存 → 再次出征。
失败路径：战斗死亡或主动撤退 → 对应结果处理 → 回城，不能死锁、重复领奖或丢失已保存角色。

现版main.gd启动直接restart进入房间，finished/victory只表达战斗结果，HUD结算主要提供重新挑战。
尚缺城镇会话、出征入口、正式奖励/背包/装备/成长、NPC事务和本地持久化；restart不能继续承担“清空整个玩家”的职责。
ws1已发布T2地图独立导出/加载/预览，尚未接入战斗；地图数据中的坐标/层序/门掩码等仍有E-INFER。
ws1交付依据见[T2记录](../reports/ws1/2026-10/2026-10-22_T2原地图加载与场景还原.md)，本区读取代码不等于代填其原版一致性验收。

## 二、首轮可玩范围

| 领域 | 首轮交付 | 后续扩展 |
|---|---|---|
| 角色 | 一名可保存角色，现有职业/武器与代表技能可用，身份明确 | 更多职业/完整技能树、多角色 |
| 城镇 | 一处可走动城镇、出征口、任务NPC、补给/装备服务 | 更多城镇、仓库、复杂服务 |
| 副本 | 一个可完成地下城，入口/普通/领主房、门/落点、回访、失败与结算 | 更多副本、原版房间选择概率、完整难度 |
| 战斗 | 三连、跳跃/空斩、跑攻、后跳/格挡、代表技能、受击/死亡，真实血蓝/CD | 全部原判定/行为能力与技能内容 |
| 奖励与成长 | 金币、经验、至少一种材料与可装备掉落；属性变化影响实战 | 完整掉落表、强化/附魔/套装等 |
| NPC与物品 | 接取/完成一条任务；购买/使用补给；装备/卸下/出售 | 长任务链、完整交易/修理/强化服务 |
| 持久化 | 本地存档、继续游戏、版本号、失败恢复与重复领奖防护 | 多存档位、迁移与中途续关 |

城镇以共享库候选town/elvengard.twn及其地图链为调查入口；未查清前不将其认定为该版本最终城镇摆位。
原版数值、任务文本、素材和有效性优先取证；试验参数独立配置并标E-ADAPT，可替换，不能冒充恢复原表。
首轮按完整循环验收，不据此声称全部城镇服务、全部副本或整个60版已完成。

## 三、状态与数据所有权

| 状态 | 允许行为 | 退出条件与结果 |
|---|---|---|
| BOOT/LOAD | 选择继续/新档、校验版本、失败恢复 | 有效Profile后进TOWN；损坏档不静默覆盖 |
| TOWN | 移动、NPC、背包/装备/补给、任务、存档、出征 | 选择合法副本；保留角色持久数据 |
| DUNGEON_SELECT | 展示可选副本、条件、返回 | 进入LOADING或返回城镇，选择界面不扣重复资源 |
| LOADING | 读地图与依赖，创建Run和角色战斗快照 | 准备成功进DUNGEON；失败退城镇并清理半成品 |
| DUNGEON | 战斗、掉落、门、房间状态 | 领主清完进SETTLEMENT；死亡进FAILURE；撤退进RETURN |
| SETTLEMENT | 显示本次统计/奖励、领取/确认回城 | 同一run_id只能结算一次；返城/重进遵循同一事务 |
| FAILURE/RETURN | 失败/撤退确认与清理 | 无通关奖励，回TOWN；若后续实现复活则另有明确成本与状态 |
| SAVE | 写完整新快照、失败提示/恢复 | 写成功后显示保存完成；失败不声称已保存 |

暂停是当前状态的覆盖层，不清空会话、不推进应冻结时钟；UI焦点隔离战斗输入。
Profile负责角色ID、职业/等级/经验、金币、背包实例/堆叠、装备、任务、已提交奖励事务与设置。
Run负责run_id、副本/难度/随机种子、房间快照、战斗状态、掉落账与结果，不与Profile混为一个可随意重置的字典。
View负责城镇/战斗/HUD表现；不独立生成奖励、扣费或改玩家持久属性。

## 四、模块接口与跨区边界

| 模块 | 所有权与输入/输出 | 约束 |
|---|---|---|
| Session/流程控制 | 状态、Profile、Run；进入/退出城镇与副本 | 统一管理生命周期，不能靠每个面板直接restart |
| Map/Stage | 消费dnf_native_map/1，提供room、placement、走区、门与镜头 | ws1现有导出/加载器继续维护，源坐标和变换显式传递 |
| Combat | 角色快照、房间规则、实体；输出击杀/清房/死亡/胜利事件 | ws2负责main.gd与核心集成，表现不能替代判定 |
| Items/Rewards | 物品定义、实例ID、掉落账、run_id；输出可提交奖励与属性 | 统一去重/容量/装备检查，不能只画图标而不改变数据 |
| Town/NPC/UI | Profile读视图、交互请求；输出服务/出征/装备/任务命令 | 通过共同事务接口改数据，不重复实现存档或伤害公式 |
| Save | schema_version与Profile；输出成功/失败及可恢复快照 | 自动存档与手动保存共享同一写入入口 |

地图进入战斗前，必须明确：源坐标→逻辑地面坐标→屏幕坐标、房间边界、相机限制、门ID/方向/目标/落点、阻挡与实体出生记录。
T2验证场景中的怪物展示是静态预览；实装时由Combat生成真实怪物，不能保留预览精灵再叠一套战斗实体。
绘制门与可通行触发分开；清房统一驱动门状态。领主结束后走结算，不从门绕过结算。
房间往返保留清理/破坏/掉落状态；开始新Run才重置本次副本，不清空Profile。

ws1先稳定T2装配与上述地图接口，可继续城镇地图/表现候选调查；新增城镇UI须先约Profile/Session请求接口。
ws2承接流程、战斗核心、奖励/物品/存档及集成；不同时改ws1的export_dnf_map.py/native_map_loader.gd。
共同文件按协作总纲登记占位；本页不代替ws1认领，也不自动向其它会话发消息。

## 五、奖励与存档底线

1. 每次出征有独立run_id；拾取/任务/通关有稳定事务ID，结算/回城/重载都不能重复发放。
2. 背包满时明确保留在地面、待领取或邮件等哪一处；首轮采用待领取记录，不静默删除掉落，不阻塞回城。
3. 购买、出售、装备、任务交付先校验再一次性变更；失败不扣一半金币、不重复消耗任务物品。
4. 经验/等级/装备属性有统一计算入口并传给下一次/当前允许更新的战斗快照；显示数值必须与实际伤害一致。
5. 存档写新完整快照后再替换，保留可恢复旧快照。测试用隔离目录，不覆盖用户真实存档。
6. 首轮不承诺中途续关：未结束的Run在重启后按显式规则回城；已提交拾取/奖励保留，未提交结果不补发通关奖励。
7. 死亡/撤退、满包、重复确认、切房/回城途中失败、保存失败与重载均需专门验证。

掉落概率、收益、回血回蓝、死亡/撤退保留内容等未核实项必须进入配置与适配记录，不能从旧工程或其它版本自动套用。
上述事务与恢复要求是本地工程的可靠性规格，不声称原客户端内部采用同样架构。

## 六、实施顺序与验收

| 阶段 | 交付与验收 | 依赖 |
|---|---|---|
| L0 接口与材料 | Session/Profile/Run接口、地图坐标/门协议、城镇/NPC/UI来源与缺口清单 | 阅读T2交付；未核实项保持显式 |
| L1 出征回城 | 城镇→选副本→入场→领主→结算→回城；死亡/撤退可回城 | 单一流程状态机；先复用现有战斗样板验证生命周期 |
| L2 可保存循环 | 任务/购买/消耗/掉落/经验/装备/结算/存档真实贯通 | Profile、物品/奖励事务；不能只做菜单跳转 |
| L3 原地图与品质 | 用ws1地图替换验证布局，对齐城镇/副本/HUD、动作与战斗 | 坐标/门协议稳定，原版证据分项补齐 |
| L4 连续游玩 | 两次出征、成功/失败/重开、装备改变战斗、退出重载完整回放 | 前述功能与原版品质分别验收 |

L1可在原版取证同时推进；当前样板只是集成测试基线。L3必须纳入首轮可玩交付，不能用流程跑通抵消五类品质问题。
验收主线：读档进城 → 接任务/买药 → 出征 → 战斗/拾取/用药 → 领主结算 → 回城交任务/装备 → 保存退出 → 重载 → 再出征，保留真实数据且无重复收益。
另验死亡/撤退、缺蓝/缺钱、满包、重复结算、加载/保存失败、焦点与暂停。
自动化覆盖真实状态和数据，另交从实际启动入口操作的连续录像；数值检查不替代美术/手感验收。
