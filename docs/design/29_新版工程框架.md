# 新版工程框架

> 适用 `game_dnf/`。目标：模块解耦、多工作区并行开发不撞车、战斗以60版原版数据驱动。
> 子文档：[战斗内核](29_新版工程框架_战斗内核.md)、[接口契约](29_新版工程框架_接口契约.md)、[内容编译](29_新版工程框架_内容编译.md)、[战斗内核实装 F3~F5](29_新版工程框架_战斗内核实装.md)。
> 分工以[28分工与共享](28_工作区分工与原版资料共享.md)为准（ws1战斗、ws2完整循环与地图接入）；本页给出两侧共用的分层与通信规则，细化战斗侧结构。ws2侧模块的内部结构由ws2自定。

## 一、为什么要先定框架

用户2026-10-22确认：战斗（打击感、跳字、UI、技能、动作）以60版为最低目标，先打底层；底层尽量直接消费原版数据，不另行设计，也不依赖逐项录屏。

现状阻碍（来自代码）：

| 问题 | 位置 | 后果 |
|---|---|---|
| 单体主脚本 | `game_dnf/scripts/main.gd` 约27KB，同时管输入、模拟、表现、音效、房间流程 | 任何两项工作都要改同一文件 |
| 测试穿透内部 | `game_dnf/scripts/test_drive.gd` 直接读写主脚本约40个字段/函数 | 重构即大面积断测试 |
| 规则手写 | `game_dnf/data/combat.json` 的窗口/距离/伤害为适配值 | 原版字段无处落地 |
| 表现与规则混写 | 停帧、震屏、跳字、音效在 hit_enemy 里一起改 | 调手感必然碰判定 |

## 二、分层与依赖方向

```
L0 离线编译   tools：PVF/ANI/IMG → 内容包（不入运行时）
      ↓
L1 内容库     ContentDB：只读查询；基线 → 适配 → 超越层 叠加
      ↓
L2 模拟内核   Combat World：纯逻辑、确定性；吃命令，吐事件与快照
      ↓
L3 流程服务   Session/Run/Profile、Map、Items、Save：生命周期与持久数据
      ↓
L4 表现与UI   ActorView/FX/跳字/镜头/音频/HUD：只读快照与事件，只发命令
```

硬规则：

1. 依赖只能向下。L2 不知道 L3/L4 存在；L4 不直接改任何状态，只发命令。
2. L2 不使用 Node、`Time`、全局随机；时钟与随机种子由外部传入，同输入必得同结果。
3. 跨模块只走对方的公开入口（每模块一个 api 文件），不读写对方内部字段。
4. 运行时不解析 PVF；所有原版数据经 L0 编译为带证据标记的内容包。

## 三、目录与模块

目标目录（F0 建立，现有 scripts/ 按迁移路线逐步搬入）：

```
game_dnf/
  main.gd            组合根：只装配模块，不写逻辑
  core/              事件总线、日志、几何(Box6)、ID、确定性随机
  content/           ContentDB：加载内容包、叠加适配/超越层、查询
  combat/
    world/           World、Entity、每帧管线
    action/          ANI时间线执行器、动作图、取消规则
    hit/             盒体变换与相交、命中去重
    resolve/         伤害管线、受击反应、停帧
    fields/          原版字段处理器（一字段一文件，自动发现）
    control/         玩家控制器、怪物AI控制器
    status/          Buff/异常
  map/               地图装配、走区、阻挡、门（ws2，T2加载器迁入）
  flow/              Session/Run/Profile 状态机（ws2，27 LOOP-01）
  items/  save/      物品奖励、存档（ws2，27 LOOP-04/06）
  view/              ActorView、FxView、跳字、镜头、音频路由
  ui/                HUD与窗口，一控件一脚本（自动发现）
  debug/             TestAPI门面、盒体叠加、事件时间轴、输入回放
  tests/<模块>/      各模块独立测试场景
  data/override/     超越层（入库、可开关）
  assets_local/      消费副本与编译内容包（Git忽略）
```

| 模块 | 职责 | 公开入口 | 归属（依28） |
|---|---|---|---|
| core | 事件、几何、随机、日志 | 各文件即入口 | ws1建立；F0后改动需登记占位 |
| content | 战斗内容包加载/查询/叠加 | content/api | ws1 |
| combat | 模拟内核全部 | combat/api（World） | ws1 |
| view | 战斗表现与反馈 | 订阅事件，无对外API | ws1 |
| ui（战斗HUD） | 血蓝/技能/CD/怪物反馈 | 读快照+发命令 | ws1 |
| map | 地图装配与走区查询（T2基线） | MapQuery | ws2 |
| flow / items / save / town | 生命周期、物品奖励、存档、城镇 | 各自 api | ws2 |
| ui（城镇/背包/结算） | 流程侧界面 | 读视图+发命令 | ws2 |
| debug | 测试门面与工具 | debug/test_api | 战斗部分ws1，流程部分ws2 |

L0 编译：解析公共工具（IMG/ANI读取、PVF token 解码）与资源发布由ws2供应；ws1新增战斗内容编译器，只调用公共工具，公共工具需改动时按28写契约交接。

## 四、模块间怎么通信

四种方式，接口格式见[接口契约](29_新版工程框架_接口契约.md)：

| 方式 | 方向 | 用途 | 例 |
|---|---|---|---|
| 命令 | L4/L3 → L2/L3 | 请求改变状态 | 输入按键、使用物品、出征 |
| 事件 | L2/L3 → 任意上层 | 已发生的事实，一对多 | 命中、伤害、死亡、清房 |
| 快照 | L2 → L4 | 每帧只读状态 | 位置、ANI与时钟、血蓝、CD |
| 查询 | 上 → 下 | 同步读取 | ContentDB、MapQuery 走区判断 |

表现层的打击感只消费事件：停帧画面、震屏、跳字、音效、特效各由独立组件订阅，调手感不碰判定。

## 五、并行开发规则

1. **新增即新文件**：字段处理器、HUD控件、反馈组件放进对应目录即被自动发现，不改任何注册表或主脚本。
2. **事件名带模块前缀**（如 combat.hit、map.room_cleared），各模块自己声明，不设中央枚举文件。
3. **共享文件最小化**：只有 main.gd、core/ 与接口契约文档属于共享文件，改前在[工作区登记](../project/03_工作区登记.md)占位。
4. **依赖检查自动化**：`tools/check_dnf_deps.py` 扫描 preload/load 路径，内核违反单向依赖或外部穿透内核 api 即报错，已接入 `run_dnf.ps1 -Test`。
5. **生成物不入库**：内容包由各区用同一编译器与同一资源锁本地生成，避免生成文件合并冲突；入库的只有编译器、字段处理器与超越层。
6. **每模块自带测试**：tests/<模块>/ 可单独运行；集成测试只经 debug/test_api，不再直接读写内部字段。
7. **契约变更先改文档**：改事件/命令/快照字段，先改接口契约并在交接日志说明，再改代码；只增字段不删改的变更可直接做。

## 六、60版基线与超越层

内容库按三层叠加，后者覆盖前者：

| 层 | 来源 | 证据 | 可否关闭 |
|---|---|---|---|
| 基线 | L0 从原版编译 | E-PARSE 起 | 否 |
| 适配 | 原版语义未知时的临时值 | E-ADAPT，必须注明原因 | 否（查清后删除） |
| 超越 | 达到60版后的手感增强 | 用户认可的设计 | 是，GM面板整体开关 |

规则：适配层只能填"未知"的位置，不能覆盖已解析的原版值；超越层可以覆盖任何值，但关闭后必须回到纯基线。
覆盖率可量化：编译器输出"字段出现次数 / 已有处理器"报告，作为底层完成度指标。

## 八、已定决策

迁移方式：渐进替换（用户2026-10-22"开搞吧"，按本节原建议执行）。战斗内核归属由28定为ws1。

## 九、表现还原底线

所有画面元素必须是原版资源和原版表现：程序画的条框、系统字体、自制颜色都算占位，只允许出现在调试叠加和资源缺失报错页。
缺原版资源时登记缺口、按28请ws2补资料，不先做替代品上线；框架迁移阶段不新增任何占位。
现存占位与替换计划：[战斗表现还原缺口](../tasks/design_tasks/ws1_combat_fidelity_gaps_v1.md)。

## 十、代码约定

- 内核（core/content/combat）只能依赖更低的内核模块，不引用 scripts/ 等过渡代码（桥接白名单除外）；任何模块访问 content、combat 都只经其 `api/`，core 整体公开。
- 内核以上（map/flow/items/save/town/view/ui）的内部组织与迁移期对 scripts/ 的使用由所属工作区自定，依赖检查不干预。
- 跨文件引用用 preload 常量，不使用 class_name，避免多区新增同名全局类冲突。
- 新增内核模块目录时同步更新 `tools/check_dnf_deps.py` 的层级表。
